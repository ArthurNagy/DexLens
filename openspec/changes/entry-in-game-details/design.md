# Design

## Context

See proposal.md for why. The entry reads one `SpeciesDetail` from the prebuilt, read-only `DexDatabase`, plus downloaded
flavor text from `ContentDatabase`. The prebuilt file is generated by `tools/build_database.py` from Room's exported schema
and a pinned PokeAPI commit, and `DatabaseModule` already falls back to a destructive migration, so a new schema version
just recopies the asset.

PokeAPI at the pinned commit has level-up learnsets for every version group up to Scarlet / Violet (about 162,000 rows) and
wild encounters for every version up to Sword / Shield and its DLC. Brilliant Diamond / Shining Pearl, Legends: Arceus,
Scarlet / Violet and Legends: Z-A have no encounter rows.

Form factors: `:app` only (phones, foldables, tablets). The entry is a single column capped at `maxContentWidth`, so the new
section needs no separate wide layout. On wide windows the entry is the detail pane and has no predictive pop of its own.

## Goals / Non-Goals

**Goals:**
- Answer "what does it learn and where do I catch it" for the game being played, offline.
- Keep the APK growth to a couple of megabytes.
- One back animation, whichever way the user goes back.

**Non-Goals:**
- Any move list beyond level up, encounter rates or conditions, or location data PokeAPI does not have.

## Decisions

### 1. A game is a version group

The picker lists PokeAPI version groups ("Scarlet / Violet"), labelled with the versions' names in the display language
joined by " / ". Learnsets are per version group, so moves need no merging. Encounters are per version, so each location
keeps the set of versions it appears in and names the one it is limited to. Twenty-odd choices fit a dropdown, where
forty-odd single versions would not.

The builder leaves out the Japan-only groups (Red / Green, Blue in Japan) and folds the Sword / Shield and Scarlet / Violet
DLC versions into their base versions, so DLC areas show under Sword / Shield.

Alternative: one choice per version. Rejected for the list length and the duplicated move lists.

### 2. Bundled tables, two of them without row ids

New entities in `:core:database`, schema version 2:

| Table | Columns | Rows |
|---|---|---|
| `version_group` | id, generation, sort_order, has_encounters | ~25 |
| `game_version` (extended) | + version_group_id | 53 |
| `version_name` | version_id, language_id, name | ~550 |
| `move` | id, type_id, power | ~940 |
| `move_name` | move_id, language_id, name | ~10,000 |
| `move_past_value` | move_id, version_group_id, type_id, power | ~1,200 |
| `learnset` | variety_id, version_group_id, move_id, level | ~160,000 |
| `encounter` | variety_id, version_id, location_id, method_id, min_level, max_level | ~37,000 |
| `location_name` | location_id, language_id, name | ~5,000 |
| `encounter_method` | id, identifier, name, sort_order | ~66 |

`learnset` and `encounter` are written as `WITHOUT ROWID` tables by the builder: their composite primary key then holds
the rows, rather than a rowid table plus an index that repeats every column. That halves the learnset table (5.3 MB to
2.1 MB). Room validates tables by columns, primary key and the indices it created (`origin = 'c'`), so the clause does
not affect validation. The database grows from 2.0 MB to 5.2 MB, and its deflated size in the APK from 0.9 MB to 2.3 MB.

Encounters are stored per location rather than per location area, with the level range merged, which keeps them at about
37,000 rows. `encounter_method` keeps PokeAPI's identifier (methods that differ only in rate, such as the three headbutt
trees, share one) and its English description. The entry words each identifier with an `entry_method_*` string resource,
so the labels translate, and falls back to the English description for the few one-off events without a string. Game
names are kept as a list of version names and joined in the screen with a translatable separator.

`move_past_value` holds, for each move and each earlier version group, the type and power in effect when the
`move_changelog` says they later changed. A learnset query left-joins it, so "Bite is Normal in Red / Blue" needs no logic
in Kotlin.

Alternative: one packed text column per variety and game. Smaller, but it hides the data from SQL and from the DAO tests.

### 3. Battle-only forms use the default variety

58 varieties have no learnset or encounter rows, all of them battle-only forms (Megas, Gigantamax). Some battle-only forms
do have a partial learnset of their own, such as Mega Venusaur in a few games. A battle-only form is the same Pokémon you
catch and train, so the repository reads the species' default variety for a variety whose default form is battle-only, or
that has no rows at all (`GameDao.usesOwnData`). Mega Venusaur shows Venusaur's moves, and Alolan Vulpix keeps its own.

### 4. Domain and use cases

- `:core:model`: `Game(id, versions, hasLocationData)`, `EncounterMethod(identifier, name)`, `LevelUpMove(level, name, type, power)`,
  `WildEncounter(location, method, minLevel, maxLevel, onlyIn)`, `GameDetails(game, moves, encounters)` and
  `InGame(games, details)`. Level 0 means learnt on evolution. A move's type is null for the old "???" type (Curse
  before Generation 5), which has no `PokemonType`.
- `:core:domain`: `GameRepository` with `games(varietyId)` (newest first) and `details(varietyId, game)`;
  `GetInGameDetailsUseCase(varietyId, requestedGameId)` picks the requested game when listed, else the stored preference
  when listed, else the newest, and loads its details; `SetPreferredGameUseCase(gameId)`.
- `UserPreferencesRepository` gains `preferredGame: Flow<Int?>` and `setPreferredGame`, stored as an int key next to the
  theme. Only an explicit pick is stored, never the default choice.
- `:core:data`: `OfflineGameRepository` over a new `GameDao`. It groups encounter rows by location and method, merges the
  level range, and fills `onlyIn` with the version names when the location is not in every version of the group.

### 5. Entry state

`EntryState.Loaded` replaces `flavor: List<FlavorEntry>` with `description: String?` and adds `inGame: InGameState?`
(games, selected game, details). Picking a game updates `selected` at once and stores the preference, and details that
arrive for a game or variety that is no longer selected are dropped. Selecting a variety reloads the in-game section, keeping
the chosen game when the new variety has it.

The description is the newest downloaded text: `OfflineFlavorTextRepository` orders entries newest first by version id,
and the ViewModel takes the first one. `SpeciesDetail.otherNames` is removed, since nothing shows it any more.

### 6. Predictive back uses the pop transition

`AppNavigation` passes the same fade for `popTransitionSpec` and `predictivePopTransitionSpec`. A predictive pop is a
seekable transition, so the shared artwork's bounds follow the gesture's progress, and the entry no longer runs
Navigation 3's default `scaleOut(0.7)` while the artwork leaves it.

## Risks / Trade-offs

- [PokeAPI has no locations for the newest games, which players are most likely to play] → the section says so plainly
  instead of looking empty, and the data improves with a later PokeAPI pin.
- [Move power and type follow `move_changelog`, which may miss a change] → the values are PokeAPI's, the same source as
  everything else.
- [Locations are PokeAPI's English names when a language has none] → the same fallback names use.
